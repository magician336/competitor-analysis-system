## 四、暂停原因：后续计划重复造轮子审查发现

对照 week3 已有接口（`backend/services/agent_service.py`、`backend/services/benchmark_service.py`、`backend/routers/{agents,benchmarks,rag}.py`、`backend/main.py`、`agents/` 层），审查 Plan 1 Task 3–10 + Plan 2，发现以下问题：

### 🔴 严重

**1. Task 9 把冻结的 16 个 benchmark task 落 DB 又残缺重建，违背 week3 已有接口。**
- Plan 1 Task 9 的 `list_tasks_from_db` 从 DB 行重建 `BenchmarkTask` 时填 `prompt=""`、`expected_behavior=""`、`task_revision="1.0.0"`、`protocol_version="week3-frozen-v2"` 等硬编码默认，**且不读 DB `metadata` JSON 里的 `success_criteria`/`tags`/`primary_dimensions`**——信息丢失。
- week3 的 16 个任务是**冻结只读**数据，`BenchmarkAgent.load_tasks()` 已返回完整 `BenchmarkTask`，现有 `/api/benchmarks/tasks` 已通过 `service.list_tasks()` → `agent.load_tasks()` 返回完整数据。
- **正确做法**：GET `/tasks` 直接复用 `BenchmarkAgent.load_tasks()`；DB 只存 runs（手工导入结果），不存/不重建 tasks。
- 同理 `list_runs_from_db` 的 `BenchmarkRun(run_id=..., task_id=str(r.task_id), ...)` 把 DB int PK 转字符串，但 `BenchmarkRun.task_id` 期望 `"bench_001"` 字符串——**类型 bug**；应复用 `BenchmarkAgent.load_runs()`，或 join `BenchmarkTaskRow` 取 `task_id` 字符串。

**2. Task 5 硬编码 5 个竞品 ID，违背 CLAUDE.md 唯一来源约束。**
- Plan 1 Task 5 的 `scripts/seed_db.py` 写了 `REQUIRED_COMPETITORS = ["cursor", "github_copilot", "trae", "tongyi_lingma", "codegeex"]`。
- CLAUDE.md 明确：`scripts/data_pipeline.py` 的 `REQUIRED_COMPETITORS` 是唯一来源，`doctor` 强制校验。
- **正确做法**：`from scripts.data_pipeline import REQUIRED_COMPETITORS`。

### 🟡 中

**3. Task 8 自造 `workflow_id`，未复用 week3 工作流元数据。**
- `persist_run_result` 用 `wf_id = f"wf_{run_type}_{int(_time.time()*1000)}"` 自造 ID。
- CLAUDE.md：`MultiAgentOrchestrator` 已提供"稳定工作流 ID、相同请求去重与有界缓存"。`MultiAgentAnalysisResult`（`schemas/orchestration.py`）很可能已带 `workflow_id`/`trace`/`branch_timings`/`model_status`（重启时需确认）。
- `workflow_to_row` 接受 `trace`/`branch_timings`/`model_status`/`rag_query_ids` 等字段，但 `persist_run_result` 一个都没传。应从 Agent 结果提取复用。

**4. Task 4/7 `BriefingResponse` 迁移改变字段结构，破坏现有契约。**
- 现有 `backend/routers/agents.py` 的 `BriefingResponse`（行 27–31）：`competitor` / `markdown` / `cards: list[IntelligenceCard]`（必填）/ `snapshot: CapabilitySnapshot`（必填）。
- Plan 1 Task 4 的 `schemas/report.py` 的 `BriefingResponse`：`competitor` / `markdown` / `card_ids: list[str]` / `snapshot: CapabilitySnapshot | None`。
- 迁移会把 `cards` 改成 `card_ids`、`snapshot` 由必填改可空，**破坏现有 `/api/agent/briefing` 响应契约**。需协调两处（或保留 agents.py 版本不动，reports 用新结构）。

**5. Task 3 `row_to_card`/`row_to_snapshot` 用 `row.competitor.code` 但 relationship 不存在。**
- 已核实 `backend/models/artifacts.py`：`IntelligenceCardRow`/`CapabilitySnapshotRow`/`BriefingRow` 只有 `competitor_id` FK，**无 `competitor` relationship**（仅 `reference.py` 的 `CompetitorRow`/`DocumentRow` 有双向 relationship）。
- `row.competitor` 会 AttributeError。需给 3 个模型加 `competitor` relationship，或改 converter 签名传入 `competitor_code`。

### 🟢 低

**6. Task 3 `task_to_row` 的 `metadata=` 遮蔽 `Base.metadata`。**

## 八、关键设计决策摘要（供重建参考）

- **混合 DB 建模**：核心实体（competitor/document/workflow）用关系表 + FK；Agent 产出物的嵌套明细（evidence/facts/impacts/dimensions/matrix）用 JSON 列。
- **ORM 类加 `Row` 后缀**（如 `IntelligenceCardRow`），避免与 Pydantic `IntelligenceCard` 同名混淆。
- **`:memory:` 用 `StaticPool`** 共享连接，让表跨请求持久；SQLite WAL + `foreign_keys=ON` pragma。
- **service 层是 DB 访问唯一入口**，每请求新建 + session 隔离（非单例，与 `agent_service` 单例模式不同）。
- **`CODERADAR_DB_PATH`** env 控制路径，`:memory:` 用于测试；`data/runtime/coderadar.db` 是默认。
- **错误处理**复用 `_service_error` 模式：`ValueError`/`KeyError`→400，服务不可用→503，未找到→404。
- **复用现有 Pydantic 契约不得覆盖**：`schemas/intelligence_card.py`、`schemas/capability_snapshot.py`、`schemas/comparison.py`、`schemas/benchmark.py`、`schemas/document.py` 是契约层，新 API 响应模型放新文件。

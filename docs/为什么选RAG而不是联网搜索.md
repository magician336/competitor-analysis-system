# 为什么选 RAG 而不是联网搜索

> 从三个递进问题理解 Mini-RAG 的设计取舍。

---

## Q1：为什么 Mini-RAG 能用自然语言查询？

传统检索系统（SQL、ES Query DSL）要求结构化语法，但 Mini-RAG 通过**三层接力**解决自然语言到结构化检索的转换：

### 第一层：QueryParser 从问句中提取过滤条件

```
输入："Cursor 最近有哪些 Agent 能力更新"

解析结果：
  competitor    = "Cursor"             # 关键词匹配竞品别名
  event_type    = ["product_release"]  # "更新" 命中事件关键词
  dimension     = ["agent_context"]    # "Agent" 命中维度关键词
  time_window   = 30 天                # "最近" 命中相对时间正则
```

解析不出来的部分也不影响——只是不传过滤条件，BM25 仍然能全文搜。

### 第二层：BM25 本身就是为全文搜索设计的

"Agent 能力更新" → ES 自动分词为 `["agent", "能力", "更新"]` → 去 content / title / heading_path 中做词项匹配 → TF-IDF 排序。不需要 `WHERE` 子句。

### 第三层：Dense 检索弥补词法匹配的盲区

BGE-M3 把问句和所有 Chunk 映射到同一个语义向量空间。即使问句与索引原文**没有公共词**：

- 问："编程助手能不能理解整个项目"
- 索引里有："Project-level context awareness across multiple files"

BM25 搜不到，但向量距离很近，Dense 能召回。

---

## Q2：LLM 已经能说人话了，为什么还需要 RAG？

LLM 有三个致命缺陷，RAG 恰好逐一补齐：

### 缺陷一：知识是冻住的

LLM 的知识截止于训练日期，它不知道昨天发生的事。

**RAG 补齐**：爬取最新数据 → 建索引 → 查询时把最新证据塞进 LLM 上下文。

### 缺陷二：会编造（幻觉）

没有信息来源时，LLM 会一本正经地胡说八道。

**RAG 补齐**：只允许 LLM 引用本次检索白名单内的 Chunk；无证据的结论自动降置信度并标 `review_required`；模型输出过完整 Pydantic 校验，非法引用直接拒绝。

### 缺陷三：没有引用

LLM 给出结论后你无法点进去看原文，无法验证。

**RAG 补齐**：每个 `Evidence` 对象带 `url` + `char_start` + `char_end` + `source_locator`，可逐条跳转到原文精确字符位置。

> 一句话：LLM 负责说人话和推理，RAG 负责提供 LLM 不知道的、最新的、可验证的事实，并管住 LLM 不要乱编。

---

## Q3：给 LLM 接一个能联网搜索的 MCP，效果不是一样吗？

这个说法对了一半。联网搜索和 RAG 都能给 LLM 补充外部知识，但**它们在四个关键维度上有本质区别**：

### 区别一：搜索的是你控制的索引空间 vs 不可控的互联网

| 维度 | 联网 MCP | Mini-RAG |
|------|---------|----------|
| 范围 | 整个互联网 | 预设的 5 个竞品 + 固定来源 |
| 精度 | 搜索引擎决定返回什么 | QueryParser + 过滤条件是硬约束 |
| 可控性 | 低 | 高——搜什么来源、什么时间段、什么证据等级，由你定义 |

搜索 "Cursor pricing"，Google 可能返回首页（有用）、Reddit 吐槽（干扰）、三年前的博客（过期）。Mini-RAG 的过滤条件 `competitor=Cursor AND source_type=pricing AND is_current=true` 确保**只搜定价页的最新版本**。

### 区别二：证据可追溯 vs 不可追溯

联网搜索返回一段自然语言，LLM 读了生成答案。你拿到答案后**无法逐句核对**它来自哪个页面的哪个段落。

Mini-RAG 每个 `Evidence` 记录：

```
chunk_id  → chunk_abc123
content   → "Pro plan: $20/month"
url       → https://cursor.sh/pricing
char_start → 145, char_end → 167
evidence_level → A（官网一手）
```

**每一句话都能定位到原文的精确字符位置。**

### 区别三：搜索质量由你控制 vs 由 LLM 临场发挥

联网搜索依赖 LLM 构造搜索词的能力——有些模型搜得好，有些搜得差。且每次搜索彼此独立，没有记忆。

Mini-RAG 的检索由确定性代码控制：搜什么索引、加什么过滤、怎么融合排序、每一步都可审计、可复现。

### 区别四：延迟与成本

| 方案 | 典型延迟 |
|------|---------|
| 联网 MCP | 5–15 秒（构造搜索词 → HTTP 请求 → 可能再打开页面 → 读全文 → 回答） |
| Mini-RAG | 50–800 毫秒（ES 本地索引，BM25 + Dense 都查同一集群，融合排序是内存运算） |

---

## 所以这个项目为什么选 RAG 而不是联网搜索？

因为项目的目标是**竞品情报分析**，场景要求：

- **固定的 5 个竞品、固定的来源**（官网、changelog、GitHub Release、定价页）——不需要全网搜索
- **精确到版本的追踪**（"这个功能是在 2.0 引入的还是 2.1 改的？"）
- **可验证性**（情报卡片上每个结论都必须标注来源，验收时可以逐条点开原文核对）
- **离线和可复现**（raw 数据不可变，处理可重放，不需要联网也能跑出相同结果）

---

## 结论

```
RAG ≠ 联网搜索

RAG       = 在可控索引空间内做结构化检索 + 可追溯证据
联网搜索 = 在全网范围内自由搜索 + 无结构化约束

它们是不同场景的两种方案，不是替代关系。
```

# 第二周验收与第三周开发接续说明

本文基于 `docs/AI编程助手.md` 的四周计划，对当前仓库已实现内容进行梳理，并检查第二周“数据采集、清洗与 RAG”需求完成情况。同时给出第三周开发 Agent、Prompt、情报卡片、能力快照和基准测试时的接续建议。

检查时间：2026-07-16

## 1. 当前项目总体状态

当前仓库已经实现了第二周的主干工程链路：

```text
竞品与数据源配置
    -> 多源采集器
    -> 原始响应落盘
    -> 清洗、去重、版本化
    -> E1-E3 事件分类
    -> D1-D7 能力标签
    -> Mini-RAG 切分、索引、检索、排序、证据引用
    -> FastAPI RAG 接口
```

但第三周的 Agent 层目前基本还是空壳：

- `agents/*.py` 已创建但内容为空；
- `prompts/*.md` 已创建但内容为空；
- `schemas/intelligence_card.py`、`schemas/capability_snapshot.py`、`schemas/benchmark.py` 等已创建但内容为空；
- `backend/routers/agents.py`、`backend/services/agent_service.py` 等 Agent API 与服务层为空。

因此项目目前适合定位为：

> 第二周数据/RAG 基座已基本成型，第三周需要在该基座上补齐 LLM Prompt、结构化输出、Multi-Agent 编排、情报卡片、能力快照和基准测试导入。

Prompt 应统一要求：

- 明确区分事实、推断、建议；
- 不把旧版本信息当作当前信息；
- 对证据冲突输出 `conflict_notes`。

### 5.3 单 Agent 设计

建议每个 Agent 都采用同一基础流程：

```text
输入：竞品、时间范围、事件/能力过滤条件
    -> 调用 Mini-RAG 检索证据
    -> 组装 Prompt 上下文
    -> 调用 LLM
    -> Pydantic 校验 JSON
    -> 失败时重试或降级
    -> 输出结构化分析结果
```

优先实现三个核心 Agent：

- Price Agent：分析价格、套餐、额度、学生优惠、计费变化；
- Product Intelligence Agent：分析模型、Agent、IDE、上下文、工具链和功能发布；
- Sentiment & Risk Agent：分析 Issue、用户反馈、故障、隐私、安全和体验风险。

然后实现：

- Compare Agent：把三个 Agent 的结果合并为对 CodeMate Campus 的机会/威胁；
- Briefing Agent：生成 Markdown 简报；
- Benchmark Agent：处理人工录入的基准测试结果。

### 5.4 不要绕开 RAG 证据

第三周 Agent 必须从 Mini-RAG 获取证据，而不是直接读网页或直接让 LLM 自由发挥。

建议服务边界：

- `mini_rag.api.MiniRAGService.query()` 负责证据检索；
- `agents/*_agent.py` 负责分析；
- `backend/services/agent_service.py` 负责编排和 API 适配；
- `backend/routers/agents.py` 只负责 HTTP 请求/响应。

这样可以保证：

- 分析结论可追溯；
- 情报卡片能绑定证据；
- 后续可复用检索轨迹；
- 测试时可以 mock RAG 返回结果。

### 5.5 能力快照接续

能力快照不要手写固定矩阵，应由证据和规则生成。

建议首版快照逻辑：

```text
按 competitor + dimension 聚合近 N 天证据
    -> 统计证据数量、证据等级、标签置信度
    -> 结合 Agent 结构化判断
    -> 输出 0-100 分、置信度、证据数
```

首版可以先采用规则评分：

- A 级证据权重最高；
- 当前版本证据高于历史证据；
- 官方证据与可复现测试高于单条 Issue；
- 与 CodeMate Campus 教育定位相关的 D7 单独保留；
- 分值变化必须能追溯到证据。

## 6. 第三周开发前置环境设置

当前本机默认 Python 是 3.9.0，不满足项目要求。第三周开发前应先统一环境。

### 6.1 安装 Python 3.11.9

项目代码使用了：

- `X | None` 类型语法；
- `dataclass(slots=True)`；
- Pydantic v2；
- 现代 FastAPI / pytest 依赖。

因此建议固定 Python 3.11.9。

PowerShell 示例：

```powershell
python --version
py -0p
```

如果没有 Python 3.11，请先安装 3.11.9，再创建虚拟环境。

### 6.2 创建虚拟环境

在项目根目录执行：

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip check
```

如果本机没有 `py -3.11`，使用 Python 3.11.9 的完整路径：

```powershell
& 'C:\Path\To\Python311\python.exe' -m venv .venv
```

### 6.3 初始化数据目录

当前仓库没有 `data/` 目录。建议创建：

```powershell
New-Item -ItemType Directory -Force data\raw, data\cleaned, data\snapshots, data\runtime, data\samples
```

可选创建占位文件：

```powershell
New-Item -ItemType File -Force data\raw\.gitkeep, data\cleaned\.gitkeep, data\snapshots\.gitkeep, data\runtime\.gitkeep, data\samples\.gitkeep
```

注意：`.gitignore` 当前忽略了 `data/raw/*`、`data/cleaned/documents.jsonl`、`data/snapshots/*`、`data/runtime/*`，这是合理的；样例数据如果要提交，应确认 `.gitignore` 允许 `data/samples/`。

## 7. 第三周适配风险与注意事项

### 7.1 文件名与依赖清单不一致

当前仓库有：

- `requirement.txt`
- `requirements-api.txt`

但 README 中仍出现过 `docs\requirement.txt`、`requirements.txt` 的描述。当前 `git status` 也显示 `docs/requirement.txt` 和 `requirements.txt` 被删除、`requirement.txt` 为新增。

建议第三周先统一依赖文件命名，否则同学按 README 配环境会失败。

推荐保留：

- `requirement.txt`：开发和测试完整依赖；
- `requirements-api.txt`：Docker API 轻量依赖。

并同步更新 README 和 doctor 检查逻辑。

### 7.2 `.gitignore` 当前忽略 `docs/*`

`.gitignore` 中存在：

```text
docs/*
```

这会导致新建文档默认不被 Git 跟踪。已有 `docs/AI编程助手.md` 因为已被跟踪所以仍存在，但新增 docs 文件需要特别处理。

建议：

- 如果 docs 是项目交付物，应删除或收窄 `docs/*`；
- 至少允许提交 `docs/*.md`。

### 7.3 当前没有实际数据产物

第二周演示前必须补齐：

- `data/raw/`
- `data/cleaned/documents.jsonl`
- Elasticsearch 索引；
- 至少一份 `data/samples/测试数据集.csv` 或等价评测集。

没有这些产物，RAG 和 Agent 都只能做单元测试，不能做业务演示。

### 7.4 Agent 输出必须可校验

第三周最容易出问题的是 LLM 输出不稳定。必须做到：

- Prompt 明确 JSON Schema；
- Pydantic 严格校验；
- 解析失败可重试；
- 缺字段不静默吞掉；
- 置信度和证据不足要显式标记；
- 所有建议都要能追溯到证据。

### 7.5 规则标签与 LLM 标签要共存

当前规则标签已经提供：

- `event_type`
- `dimension_tags`
- `label_confidence`
- `label_reasons`
- `needs_review`

第三周不要直接覆盖这些字段。建议新增：

- `agent_event_type`
- `agent_dimension_tags`
- `agent_confidence`
- `agent_reasoning_summary`

或在情报卡片中保留规则标签与 Agent 判断的对照，以便评测“多标签 F1”和人工复核。

### 7.6 能力快照要区分事实与评分

事实来自：

- 文档证据；
- 价格页；
- Changelog；
- GitHub Issue；
- 基准测试结果。

评分是分析结果。第三周要避免把评分硬编码进代码。每个分数至少保存：

- 分值；
- 证据数量；
- 证据等级；
- 评分时间；
- 产品版本；
- 置信度。

### 7.7 第三周不要过早做复杂前端

前端是第四周重点。第三周只需要保证：

- Agent 能生成 JSON 情报卡片；
- 能保存或返回能力快照；
- 能导入基准测试结果；
- FastAPI Swagger 可调试。

## 5. Benchmark 正式执行流程

对每个产品、每个任务都按下列顺序执行：

1. 记录产品版本、模型、系统时间、机器配置和评测人员；
2. 从原始 starter 复制一个干净候选目录；
3. 从 `run_task --audit` 保存任务修订/指纹、验证器/协议和 starter SHA-256；
4. 使用相同原始 Prompt、工具权限、最大轮次和超时；
5. 保存每轮对话、工具调用、diff 和人工干预；
6. 对候选目录运行统一 Runner，保存 candidate SHA-256，并确认其余来源字段与第 3 步一致；
7. 解释任务由 A/B 两名匿名评审独立评分，按 `merge_rule.json` 合并；
8. 写入带完整来源字段和时区的严格 CSV 行；
9. 使用 `BenchmarkAgent.import_csv(..., persist=True)` 严格导入；
10. 只有覆盖率达到团队预设门槛后才形成正式产品比较。

```powershell
python -m benchmarks.validators.run_task `
  --task-id bench_008 `
  --candidate C:\bench-runs\cursor\bench_008
```

`manual_runs.csv` 当前为 0 条，不是遗漏；在没有真实公平执行前，保持为空比使用演示数据更正确。

```text
GET  /api/benchmarks/compare     → 覆盖率约束下比较
```

所有请求/响应继续使用第三周 Pydantic Schema，并生成 OpenAPI 示例。

## 8. 第四周开发前置决策

第四周编码前必须先完成以下决策，否则容易返工。

### 8.1 冻结领域合同

- 冻结 `IntelligenceCard`、`CapabilitySnapshot`、`CapabilityComparisonMatrix`、Benchmark Run；
- Schema 变更使用显式版本与迁移，不直接覆盖历史 JSON；
- 冻结 `week3-evidence-v2` 和 `week3-frozen-v2`；
- 定义 API 的 UTC 时区、分页、错误码、幂等键和额外字段策略。

### 8.2 补齐 CodeMate 输入

- 明确 CodeMate Campus 当前产品版本；
- 用相同 16 项任务做正式运行；
- 准备可审计的内部产品能力证据；
- 生成相同窗口、相同评分版本的 CodeMate Snapshot；
- 覆盖率达到 0.80 后再开启正式排名。

这是雷达图、差距矩阵和行动优先级上线前的硬前置。

### 8.3 选择持久化与任务方案

推荐基线：

- PostgreSQL：结构化实体、唯一约束、迁移；
- JSONB：保留原始完整 Schema，但 Evidence Link/关键查询字段要规范化；
- Redis + Celery/RQ/自有 Worker 三选一，不要并用多个队列；
- 对 `workflow_id/card_id/snapshot_id/run_id` 建唯一索引；
- 使用 request fingerprint 实现幂等提交；
- 数据库连接、队列和模型 Key 全部来自环境/密钥管理。

### 8.4 定义前端状态语义

前端必须能表达：

- `insufficient_evidence` / N/A；
- `review_required`；
- conflict；
- `partial_failure`；
- rules/hybrid/llm；
- 产品版本 unknown/mixed；
- 评分版本与窗口；
- `official_ranking_ready=false`；
- 证据等级与来源链接。

不允许把 0 当作 N/A，也不允许隐藏低覆盖警告。

### 8.5 明确安全与成本边界

- API 不接受客户端传入任意本地路径或 Shell 命令；
- Benchmark runner 只执行冻结的参数数组；
- 本地 Runner 不是 OS 沙箱，不允许直接承接公共不可信代码；执行服务必须放入一次性、最小权限、禁网或受控网络的容器/VM；
- Key 不进入数据库、Trace、日志或前端；
- 记录可获得的 Token Usage、延迟、模型、费用和重试；
- 设置每工作流预算、并发、超时和降级策略；
- 报告下载和证据查看需要鉴权和审计。

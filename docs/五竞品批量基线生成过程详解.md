## 1. 一句话

这条命令**遍历 5 个竞品，对每个竞品完整执行一次 Multi-Agent 编排（Price → Product → Risk 三 Agent 并行 → CompareAgent 快照 → BriefingAgent 简报），最后把全部竞争品的卡片、快照、简报、轨迹原子性地写入 `artifacts/week3/`。**

它和高层的 `POST /api/workflows` 走的是**完全相同的编排器代码路径**，区别在于：
- 它是串行遍历（跑完一个竞品再跑下一个）而不是并发
- 它写本地文件而不是 SQLite 数据库
- 它是一次性打包全部产物并附带清单（manifest）作为完整性标记

## 3. 第一步：参数解析与校验

**入口**：`scripts/generate_week3_baseline.py` L582-609 的 `main()` 函数

```python
def main(argv: list[str] | None = None) -> int:
    args = build_parser().parse_args(argv)
    configured = _load_competitors(PROJECT_ROOT / "config" / "competitors.yaml")
    competitors = _select_competitors(configured, args.competitors)
    ...
    manifest = generate_baseline(
        competitors=competitors, output_dir=output, mode=args.mode,
        top_k=args.top_k, allow_partial=args.allow_partial,
        as_of=args.as_of, window_days=args.window_days,
    )
```

参数校验规则（`build_parser()` L537-579）：

| 参数 | 默认值 | 约束 |
|---|---|---|
| `--competitors` | `"all"` | 逗号分隔的名称，或 `"all"` 表示 5 个全部 |
| `--mode` | `"rules"` | 必须是 `rules` / `hybrid` / `llm` |
| `--top-k` | `8` | 1–30 |
| `--as-of` | 当前 UTC 时间 | ISO 8601 时间戳或 `YYYY-MM-DD`，必须 UTC |
| `--window-days` | `90` | 1–3650 |
| `--allow-partial` | `False` | 开关，允许部分分支失败时仍写出产物 |
| `--output` | `artifacts/week3` | 输出目录路径 |

**竞品别名映射**（L128-135）：

`_load_competitors` 读 `config/competitors.yaml` 的 `competitors[].name` 字段，返回顺序与 YAML 定义一致。`--competitors all` 会展开为五个配置中的全部竞品。

## 4. 第二步：时间窗计算与输入指纹记录

**时间窗**（`_analysis_window()` L86-107）：

```python
end_time = as_of  →  2026-07-20T23:59:59.999999+00:00
start_time = end_time - 90 days  →  2026-04-21T23:59:59.999999+00:00
```

时间窗会被透传给每个 Agent 的 `RAGQuery`，限制只检索该窗口内的证据。

**输入指纹**（L373-386）：

计算三个文件的 SHA-256，写入 manifest 的 `input_sha256` 段：

| 键 | 文件路径 | 用途 |
|---|---|---|
| `tasks` | `benchmarks/tasks/tasks.jsonl` | 16 个基准任务定义 |
| `scoring` | `config/scoring.yaml` | D1-D7 评分权重配置 |

这些哈希在后续验收时会被 `verify_week3_delivery.py` 重新校验（L892-905），确保基线产物与当时的输入严格对应。

## 6. 第四步：创建编排器

**代码**：L397-400

```python
workflow = MultiAgentOrchestrator(
    rag_service,
    auto_configure_llm=mode in {"llm", "hybrid"},
)
```

`auto_configure_llm=True` 意味着：
- 三个专家 Agent 在构造时自动调用 `LangChainLLMClient.from_env(mode=mode)`（`agents/base.py L93-96`）
- `hybrid` 模式：检查 `DEEPSEEK_API_KEY`，缺了立即报错；有了就构造 `ChatDeepSeek`
- 如果不传 `auto_configure_llm`（默认 `True`），但环境中 `CODERADAR_AGENT_MODE` 是 `rules`，`from_env()` 返回 `None`，三个 Agent 也会以无 LLM 模式运行

对比 `--mode rules` 时的行为：

| | `--mode hybrid` | `--mode rules` |
|---|---|---|
| `auto_configure_llm` | `True` | `False` |
| 构造 `ChatDeepSeek` 吗 | 是（需 API Key） | 否 |
| 卡片有无 LLM 润色 | 有（失败回退） | 无，全程代码生成 |

## 7. 第五步：逐竞品执行编排

**这是最核心的一步**（L402-427）：

```python
for competitor in competitors:
    result = workflow.run(
        MultiAgentAnalysisRequest(
            competitor=competitor,
            top_k=top_k,
            correlation_id=f"week3-baseline-{_safe_filename(competitor)}",
            include_snapshot=True,
            include_briefing=True,
            include_benchmark_data=True,
            use_cache=False,
            start_time=start_time,
            end_time=end_time,
        )
    )
```

### 7.1 请求参数详解

| 字段 | 值 | 含义 |
|---|---|---|
| `competitor` | `"cursor"` 等 | 竞品名 |
| `top_k` | `8` | 每分支检索返回最多 8 条证据 |
| `correlation_id` | `"week3-baseline-cursor"` 等 | 用于日志追踪和幂等 |
| `include_snapshot` | `True` | 生成 D1-D7 能力快照 |
| `include_briefing` | `True` | 生成 Markdown 简报 |
| `include_benchmark_data` | `True` | 从 CSV 加载基准数据供快照评分 |
| `use_cache` | `False` | 不命中进程内缓存，确保每次都重新执行 |
| `branches` | 默认 `[price, product, risk]` | 三个分支全开 |

### 7.2 单竞品编排内部流程

```
workflow.run(MultiAgentAnalysisRequest)
  │
  ├─ _execute()
  │   │
  │   ├─ _selected_pipeline([price, product, risk])
  │   │   └─ RunnableParallel({
  │   │        "price": safe_price_agent,    → PriceAgent.run()
  │   │        "product": safe_product_agent,→ ProductAgent.run()
  │   │        "risk": safe_risk_agent        → RiskAgent.run()
  │   │      })
  │   │
  │   ├─ 三个分支并行执行
  │   │   └─ 每个分支内部（EvidenceBackedAgent.run）：
  │   │       ├─ _prepare_query → RAGQuery（含 competitor + event_type + top_k + 时间窗）
  │   │       ├─ _retrieve_evidence → MiniRAGService.query() → RAGResponse（8 条 evidence）
  │   │       └─ _compose_result → 证据守卫 → 事件聚类 → 规则卡片 → [LLM 润色] → IntelligenceCard[]
  │   │
  │   ├─ 汇总三个 BranchOutcome
  │   │   ├─ 成功分支：卡片去重
  │   │   └─ 失败分支：记录 warning
  │   │
  │   ├─ BenchmarkAgent.load_tasks() + load_runs()
  │   │
  │   ├─ CompareAgent.build_snapshot()  → CapabilitySnapshot
  │   │   └─ 根据 cards 中的 impact_details + benchmark runs
  │   │       ├─ 对 D1-D7 逐维计算证据分（evidence_score）
  │   │       ├─ 对 D1-D7 逐维计算基准分（benchmark_score）
  │   │       └─ 加权合并 → 最终分 + 置信度 + 状态
  │   │
  │   ├─ BriefingAgent.generate()  → Markdown 字符串
  │   │   └─ 9 段结构化简报（摘要 + 最新变化 + 能力观察 + 风险信号 + 快照表格 + 证据索引 + 复核项）
  │   │
  │   └─ 返回 MultiAgentAnalysisResult
  │       ├─ status: SUCCESS / PARTIAL_FAILURE / FAILED
  │       ├─ cards: IntelligenceCard[]（~7 张）
  │       ├─ snapshot: CapabilitySnapshot
  │       └─ briefing: str（Markdown）
  │
  ├─ 校验
  │   ├─ FAILED?                    → raise RuntimeError（全部中断）
  │   ├─ PARTIAL_FAILURE? 且不 allow_partial → raise RuntimeError
  │   └─ snapshot/briefing 为 None? → raise RuntimeError
  │
  └─ 添加到 results 列表
```

### 7.3 串行 vs 并行的理解

虽然每个竞品内部的三个分支是**并行**的（`RunnableParallel`），但五个竞品之间是**串行**的。

```
时间 →
cursor ───┬─ price ───┬─ RAG ── 证据守卫 ── [LLM] ── 卡片1
          ├─ product ─┤                                   ├─ CompareAgent → BriefingAgent → result1
          └─ risk ────┘                                   │
                                                           │
github_copilot ───┬─ price ───┬─ ...                       │
                  ├─ product ─┤                            ├─ CompareAgent → BriefingAgent → result2
                  └─ risk ────┘                            │
                                                           │
trae ─── ...                                               │
                                                           │
tongyi_lingma ─── ...                                      │
                                                           │
codegeex ─── ...                                           │
                                                           ▼
                                                   汇总 → 原子写入
```

这样设计的理由：避免 15 个 Agent（3 × 5）同时调 ES 和 DeepSeek API 造成资源争抢，同时也让错误隔离更干净——一个竞品失败不会影响其他竞品的结果（除非 `--allow-partial` 为 `False`）。

### 7.4 校验条件（L416-426）

```python
if result.status == WorkflowExecutionStatus.FAILED:
    raise RuntimeError(f"all specialist branches failed for {competitor}")

if result.status == WorkflowExecutionStatus.PARTIAL_FAILURE and not allow_partial:
    raise RuntimeError(f"partial failure for {competitor}: ...")

if result.snapshot is None or result.briefing is None:
    raise RuntimeError(f"missing snapshot or briefing for {competitor}")
```

**默认行为**（`--allow-partial` 不指定，为 `False`）：
- 只要一个竞品的任何一个分支失败 → 整个脚本中断，不写任何产物
- 这是保护基线完整性的设计：所有 5 个竞品必须都有完整的三分支 + 快照 + 简报

**`--allow-partial` 开启时**：
- 部分分支失败的竞品仍然算通过（`PARTIAL_FAILURE`），产物中包含该竞品的成功分支卡片和快照
- 中断标准放宽为只拦截 `FAILED`（全部分支都失败）

### 8.1 汇总（L429-436）

### 8.2 关键汇总函数

**`_trace_summaries(results)`**（L268-302）：

对每个 `MultiAgentAnalysisResult`，遍历其 `branch_outcomes`（`{branch: BranchOutcome}`），为每条分支生成：

| 字段 | 内容 |
|---|---|
| `workflow_id` | `workflow_<hash24>` |
| `branch` | `price` / `product` / `risk` |
| `status` | `success` / `failed` |
| `duration_ms` | 执行耗时 |
| `error` | 错误类型 + 脱敏消息（不暴露 API Key 或 prompt 文本） |
| `trace` | `AgentExecutionTrace`（阶段列表、llm_used、fallback_used、model_name） |
| `rag_query_id` | 对应的 RAG 查询 ID |
| `card_ids` | 该分支产出的卡片 ID 列表 |
| `warnings` | 脱敏警告 |

**脱敏处理**（`_redact_text()` L214-231）：在写入前过滤 API Key、Bearer Token、prompt 文本等敏感信息。

**`_effective_mode_counts(results)`**（L305-319）：

统计每个分支实际生效的模式计数——这对 `--mode hybrid` 特别重要：因为 LLM 可能部分失败回退到 rules，这条信息记录了"你以为用的是 hybrid，但实际有多少卡片走了 hybrid、多少走了 fallback"。

### 9.1 原子写入机制

`_atomic_text()`（L171-193）使用 OS 级别的原子替换：

```python
def _atomic_text(path, content):
    # 先写入临时文件（同名前缀 . 后缀 .tmp）
    with tempfile.NamedTemporaryFile(..., prefix=f".{path.name}.", suffix=".tmp", dir=path.parent) as f:
        f.write(content)
        f.flush()
        os.fsync(f.fileno())     # 强制刷盘
    # 用 os.replace 原子替换目标文件
    os.replace(temporary, path)  # POSIX 级原子操作
```

这意味着：
- 写文件过程中断电/中断，目标文件要么是旧的完整内容，要么是新的完整内容——不会出现半写
- `_write_json()` 包装 `_atomic_text()`，JSON 文件也一样保证

### 9.2 Manifest 作为完整性标记

Manifest 的写入顺序设计是一个 **commit marker** 模式：

```
① 删除 manifest.json      →  此时 artifacts/week3/ 是一堆无担保的零散文件
②-⑥ 写 5 个产物文件      →  逐个原子写入
⑦ 写 manifest.json        →  完整性标记出现
```

如果在 ①–⑥ 之间中断：manifest 不存在，验收脚本 `verify_week3_delivery.py` 会发现**清单缺失**，拒绝通过。

如果 ⑦ 之后中断：所有产物都在，manifest 也在，验收通过。

这种设计的直接结果是：**基线产物要么是全的，要么是空的，不存在中间状态。**

## 10. 错误处理策略

| 错误场景 | 行为 | 退出码 |
|---|---|---|
| Mini-RAG 未就绪（ES 没启动/索引未建） | 立即抛出 `RuntimeError`，不写任何文件 | 1 |
| `--mode hybrid` 但缺 `DEEPSEEK_API_KEY` | `LangChainLLMClient.from_env()` 抛 `ValueError`，中断 | 1 |
| 某个竞品全部分支都失败（`FAILED`） | 抛 `RuntimeError`，不写任何文件 | 1 |
| 某个竞品部分分支失败（`PARTIAL_FAILURE`），且 `--allow-partial` 未指定 | 抛 `RuntimeError`，不写任何文件 | 1 |
| 某个竞品部分分支失败，且 `--allow-partial` 已指定 | 打印警告，继续处理下一个竞品 | 0 |
| 某个竞品的 snapshot 或 briefing 为 None | 抛 `RuntimeError`（代码路径异常） | 1 |
| 写入文件时磁盘满/权限不足 | Python IOError 冒泡，中断 | 1 |
| 全部成功 | 正常退出 | 0 |

**关键设计**：除了 `--allow-partial` 开启的情况，**任何一个竞品的任何一次失败都会导致全盘不写任何产物**。这么设计是因为基线产物是一套要交付给验收和后续 Week4 使用的"冻结版本"，不允许出现"缺了 cursor 但其他四个写进去了"的不一致状态。

## 11. 产物速查

| 文件 | 结构 | 行数/条数预期 | 读取方式 |
|---|---|---|---|
| `manifest.json` | 单 JSON 对象 | — | `json.loads()` |
| `intelligence_cards.json` | JSON 数组 | ~35 张 | `IntelligenceCard.model_validate()` |
| `capability_snapshots.json` | JSON 数组 | 5 个 | `CapabilitySnapshotSet.model_validate()` → `.snapshots` |
| `workflow_summary.json` | JSON 数组 | 5 条 | 直接读 |
| `trace_summaries.json` | JSON 数组 | 15 条 | 直接读 |
| `briefings/*.md` | Markdown 文本 | 5 份 | 直接读 |

**Week3 验收脚本 `verify_week3_delivery.py` 的产物级约束**（L875-1033）：

- `intelligence_card_count` 必须等于 manifest 声明数
- `snapshot_count` 必须是 `competitor_count`（5）
- 每个 workflow 的三个分支全部必须 `SUCCESS`
- 每个 snapshot 的 `product_version` 不能是占位符（不能是 `""` / `"n/a"` / `"none"` 等）
- `evidence_backed_card_count` 必须与卡片人工核对一致
- `trace_count` 必须等于 15（3 × 5）
- 简报文件数和竞品数一致
- 对比矩阵的 `official_ranking_ready` 必须为 `false`（因没有真实 CodeMate 快照）

## 12. 与交互式工作流的对比

| 维度 | `generate_week3_baseline`（批量基线） | `POST /api/workflows`（交互式工作流） |
|---|---|---|
| **调用方式** | 命令行脚本 | HTTP API |
| **运行模式** | 一次性批量 5 个竞品 | 按需单竞品 |
| **并发度** | 竞品间串行，内部分支并行 | 单竞品，内部分支并行 |
| **缓存策略** | `use_cache=False` | 默认 `use_cache=True`（LRU 128） |
| **产出存储** | `artifacts/week3/` 本地文件 | SQLite 数据库 |
| **完整性保证** | Manifest commit marker | 事务写入 |
| **大模型** | 可选（rules/hybrid/llm） | 同上，受 Worker 配置决定 |
| **重试** | 无——失败就中断 | Worker 按 attempt 有界重试 |
| **前置依赖** | ES 索引就绪 + 环境变量 | 同左 + Worker 进程运行中 |
| **典型用途** | 交付验收、快照基线、Week4 初始化导入 | 用户按需发起的分析请求 |
